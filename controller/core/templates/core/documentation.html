Controller Configuration Guide

This guide describes the configuration controls present in release {{ vivolution_release_id }}. Follow the order below on a newly installed controller. Fields or workflows not shown in the console are not available in this release.

1. Console scope

The configuration console is an operator-only management interface. It stores customer, Microsoft 365, tenant-context and Edge inventory and tracks immutable configuration versions and audit events. It does not carry SIP or RTP traffic.

Current boundary: identity and permission records are reconciled by the privileged installer and cannot be administered through the web console. Audit events are read-only and managed records cannot be deleted from the console.

2. Before configuration

  • Confirm the controller FQDN resolves to the intended public address.
  • Confirm the browser trusts the HTTPS certificate and shows the expected FQDN.
  • Use the operator credential printed by the successful installer completion.
  • Verify /health/live and /health/ready before editing records.
  • Record the installed release identifier shown at the top of this page for support.

Open the configuration console. If sign-in is unavailable, use the recovery page and the local console rather than repeatedly guessing the operator password.

3. Recommended configuration order

3.1 Customer account

Create the legal customer boundary first. Supply a unique, stable slug and leave the account Active only while service is authorized. Slugs are used as durable identifiers and should not contain mutable branding or project dates.

3.2 Microsoft 365 tenant

Add the customer's exact Entra tenant UUID, display name and primary verified domain, then associate it with the customer account. Keep the record Pending verification until tenant ownership and voice licensing are independently confirmed; entering a UUID is not proof of authority.

3.3 Tenant context

Create the immutable technical isolation context joining one customer account to its Microsoft 365 tenant. Confirm both selections belong together before saving. Routing, configuration and audit data use this context as their authorization boundary.

3.4 Edge cluster

Add an Edge cluster with a stable name, service mode, region and lifecycle status. Shared Enhanced clusters must not select an exclusive owner. Exclusive clusters must select exactly one customer account.

3.5 Edge nodes

Register each expected Edge node under its cluster. Select the real architecture and its unique HA slot. Select exactly that node and use Issue a display-once enrollment grant. Copy the shown Controller shared URL and grant directly into the Edge installer's protected prompt; never place the grant in argv, a URL, shell history, an environment variable, a log, or a reusable image.

The node proves its locally generated Ed25519 key and enters Pending approval. Independently compare the exact fingerprint shown by the VM/cloud console, then use Approve pending enrollment claim. Status, generation, placement identity, and heartbeat observations are enrollment-driven and read-only after creation. Use Revoke current node identity to block all further node API requests. This release reports enrollment and heartbeat visibility only; it does not deliver SBC configuration or secrets.

3.6 Configuration version

Start with a Draft version for the tenant context. Review and validate the complete generated artifact before publication. A published version requires an exact lowercase sha256: digest and publication time. Never reuse a version number for different content.

3.7 Audit history

Use Audit events to investigate who performed an action, its request identifier and affected object. Audit records are intentionally read-only. Export and retain them according to the customer's approved retention policy.

4. Health and verification

GET /health/live
Confirms the web process can answer without depending on PostgreSQL.
GET /health/ready
Confirms PostgreSQL is reachable, required migrations exist, and the signed row-level-security key and policy catalog match this release.

A live but unready controller must stay out of service. Do not bypass readiness or publish configuration while it returns HTTP 503.

5. Release availability and operator sessions

One standalone Controller — available: this release installs and operates one Controller. The shared Controller FQDN must resolve only to that Controller's address.
  • Multi-controller HA — unavailable / planned. Node joining, replication, fencing, quorum and promotion have not been released or qualified.
  • External HTTPS load balancer — unavailable / planned. Health-based member removal and cookie persistence are not supported by the standalone release.
  • Multi-controller DNS round-robin — unavailable. Do not publish additional controller addresses under the shared FQDN in this release.
Session behavior: the Ubuntu standalone installer explicitly uses the local PostgreSQL session backend. Logout removes the server-side session immediately. This database groundwork does not make multi-controller HA, DNS round-robin or load balancing supported; those modes stay unavailable until their complete release gate passes.

6. Supported operations

  • Application backup and restore — unavailable / planned. This release has no supported application-level backup or restore command.
  • Release upgrades — unavailable / planned. Reconcile reapplies the installed source and configuration; it is not an upgrade command.
  • Operator password reset — unavailable / planned. Preserve the root-only initial credential file. Do not edit password hashes or database rows.

Run lifecycle operations through this exact version-pinned bootstrap:

curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' --tlsv1.2 https://raw.githubusercontent.com/vivolution/vivolution-install/v0.3.0-rc7/install.sh | sudo sh -s -- status
curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' --tlsv1.2 https://raw.githubusercontent.com/vivolution/vivolution-install/v0.3.0-rc7/install.sh | sudo sh -s -- resume
curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' --tlsv1.2 https://raw.githubusercontent.com/vivolution/vivolution-install/v0.3.0-rc7/install.sh | sudo sh -s -- reconcile
curl --fail --show-error --silent --location --proto '=https' --proto-redir '=https' --tlsv1.2 https://raw.githubusercontent.com/vivolution/vivolution-install/v0.3.0-rc7/install.sh | sudo sh -s -- support-bundle

The initial console URL, administrator name and password are stored in /var/lib/vivolution/installer/credentials.txt. Read that root-only file locally; never copy it into logs or a support bundle. The installer owns this credential. Password rotation is not available in this release, and Django's built-in password-change endpoints are deliberately blocked.

7. Troubleshooting

Check installer status first. Resume only an interrupted installation; use reconcile only after installation completed. Create a redacted support bundle when requested, inspect it before sharing, and provide the release identifier, UTC timestamp and sanitized error reason. Do not paste environment files, database URLs, cookies, private keys, credentials or complete logs into a support ticket.

8. Security boundary

  • Use HTTPS only; do not access the loopback Gunicorn listener directly.
  • Use the stable Controller shared URL printed with the grant; Edge nodes do not bind to a brand-specific domain.
  • Keep the controller, node and shared FQDN records stable and certificate-matched.
  • Grant operator access individually and remove it through the supported privileged workflow.
  • Never store tenant Global Administrator credentials in the controller.
  • Treat row-level security as a second barrier, not a substitute for application authorization.
  • Use the audit trail and immutable configuration digest for every production change.
